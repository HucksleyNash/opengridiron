## Product Decision

The Draft Room is a read-only, second-screen draft companion. It never submits a pick to Yahoo. Its job is to answer: **Given who has been drafted, the league rules, my roster, and what may survive until my next turn, who should I take and why?**

The original plan called for tiered value-over-replacement rankings, roster construction, a manual live pick board, Yahoo draft-result polling, positional-run detection, and continuously updated next-pick recommendations. A validated vertical slice now implements sessions, append-only events, manual drafting, immutable inputs, deterministic recommendations, Yahoo shadow reconciliation, exposure, diagnostics, and a basic replay. This plan replaces the vertical slice's shallow internals with the complete prepare, execute, learn suite while preserving its tables, public API contracts, session IDs, and canonical history.

Delivery decision: build and accept the Draft Suite as one full-suite release. Internal workstreams retain dependency gates, but no partial workstream is treated as the finished product.

Validation-sequencing decision: after Workstream 1 reaches its engineering gate, privately dogfood one complete standard snake mock or real draft before Workstream 2 begins. This is an unfinished owner-only validation build, not a partial product release; findings must be resolved or explicitly accepted before live intelligence depends on the manual-room workflow.

Recommendation-strategy decision: default to objective-driven adaptive advice. Named strategies are visible comparison scenarios and become authoritative only when the owner explicitly locks one for the session.

Live-source decision: live sessions begin in manual mode. Enabling Yahoo starts approval mode because real behavior is unmeasured. Exact Yahoo/manual matches auto-confirm; missing, conflicting, corrected, or unknown-player observations become explicit proposals and cannot change the canonical board without owner approval. Structured Yahoo OAuth observations outrank scraper observations when the two disagree. During an attended draft, the owner may explicitly promote a feed already validated in approval mode to auto-approve only clean next-in-sequence mapped picks; all unsafe observations remain proposals. A recorded real 50+ pick rehearsal remains the alternate gate for evidence-based promotion without live owner confirmation. Automatic events remain append-only and visible. The app never writes a pick back to Yahoo.

Canonical-state decision: use append-only draft events with a derived board, immutable recommendation snapshots, and read-only compatibility views. Mutable pick rows and board-per-turn snapshots are not independent authorities.

Event-model challenge decision: retain append-only events after outside review. The supported stream is bounded, and a pure reducer plus derived/cache views keeps corrections, reconciliation, reopening, and replay on one authority; canonical mutable picks plus a separate audit ledger would introduce a second structure that can diverge.

Yahoo-outage decision: a connected session remains usable through provisional manual entry while Yahoo is unavailable. The UI marks provider freshness and provisional events explicitly; reconnection runs the session's current shadow or evidence-gated authoritative reconciliation policy and never silently discards local history.

Security-boundary decision: preserve Open Gridiron's private, one-owner trust model. Every Draft Room endpoint is registered on the existing protected API router; hosted mutations require the existing authenticated session and CSRF check, while authentication remains disabled only in the loopback-only local profile. Multi-account tenancy, sharing, and role management are not part of this release.

AI-trust decision: owner notes, provider text, and news excerpts are untrusted evidence. When explanations use them, they are sent only inside a delimited, typed dossier and can never supply instructions, tools, scores, probabilities, or state changes. Explanation output must pass strict schema validation and factual grounding against stored inputs; otherwise it is discarded in favor of deterministic reason strings.

Import-safety decision: ranking and projection imports use a validate-preview-commit workflow. Files are bounded and staged, all identity matches, warnings, and blocking errors are shown, and no active immutable snapshot is created until the owner explicitly accepts an unchanged preview.

Identity decision: introduce canonical `Athlete` records plus one-to-many `AthleteAlias` rows keyed by provider, namespace/season scope, and external ID. League players, ranking/projection rows, news evidence, cross-league exposure, and historical snapshots must resolve through `athlete_id`; unresolved aliases remain explicit and can never fall back silently to a name-only match.

Projection-history decision: every projection import creates an immutable `ProjectionSnapshot` and canonical-athlete `ProjectionSnapshotRow` set. Sessions bind to an explicit projection version; a refresh creates a new version and explicit input-change event for future advice. Mutable `Player` projection fields become compatibility/latest-value data and are never replay authority.

Stale-interaction decision: a manual `Record pick` action must match the session sequence and recommendation snapshot currently on the server. A stale action is rejected, the canonical board and advice refresh, and the intended player remains highlighted for one fresh confirmation if still available; the server never auto-applies advice from an outdated board.

Code-organization decision: implement Draft Room as a cohesive feature module inside the existing FastAPI/React application. Keep one database and deployment, but move draft routing, schemas, reduction, reconciliation, recommendations, simulations, replay, and UI state out of the existing large general-purpose files.

Yahoo-test decision: fixture and simulated-contract tests are sufficient to release automatic Yahoo polling as live read behavior. Automatic canonical authority requires either explicit attended owner confirmation after approval-mode validation or a recorded owner-controlled Yahoo mock/live rehearsal of at least 50 consecutive picks. Runtime freshness and provisional-manual rescue states remain required in either mode.

Computation-timing decision: commit canonical events before computing advice. Produce and cache the deterministic ranking immediately after commit, outside the write transaction; run forecast refinement and multi-round simulation as cancellable enhancements that may publish only when their session sequence and input hash are still current.

Snapshot-timing decision: after canonical sequence N commits, compute and persist deterministic recommendation snapshot N outside the write transaction. An owner-team pick at expected sequence N must reference the latest ready snapshot for N and its current input hash; if none is ready, reject with retryable `advice_pending`. Never compute advice inside the event transaction or accept an owner pick without its at-time snapshot.

Execution-substrate decision: the open Draft Room browser orchestrates Yahoo polling; the server enforces a per-session single-flight sync guard and idempotent reconciliation. Deterministic advice computes immediately after event commit outside the write transaction. Forecast enhancement and user-triggered simulation run in one bounded isolated worker with sequence/hash publication checks; interrupted optional work is retryable rather than backed by a new durable queue.

Diagnostics decision: provide an owner-only redacted diagnostic bundle per draft session. It includes event chronology, versions and hashes, score components, source freshness, reconciliation outcomes, typed errors, and timing metrics, but excludes credentials, cookies, authorization headers, raw provider payloads, and owner/news prose.

Rollout decision: use one reversible feature flag for the complete Draft Suite. Additive migration, legacy import, shadow integrity checks, and smoke tests run before activation; the old Draft Room remains a temporary read-only fallback, but individual new capabilities are not released behind separate product flags.

Operational-isolation decision: retain `draft_suite_enabled` as the only user-facing product flag, plus operator-only capability switches and circuit breakers for Yahoo polling, forecasting, simulation, and AI explanations. Disabling an optional capability produces its typed unavailable state and never disables canonical manual drafting.

Frontend-test sequencing decision: build the deterministic Draft session test router and first complete Playwright draft journey before the live cockpit UI. The test harness controls sequences, provider observations, failures, time, and viewports, and is impossible to register outside the test application.

Retention decision: retain completed draft sessions, append-only events, immutable recommendation snapshots, and deterministic coaching evidence until the owner explicitly deletes a session. Deletion is owner-only, previews replay/coaching and shared-reference impact, cascades only session-owned data, and is covered by integrity checks; expired rolling backups follow the existing backup lifecycle.

Live-visual-hierarchy decision: when the owner is on the clock, the page is a decision cockpit led by three serious candidates and each candidate's why-now reason, next-turn availability, roster impact, and principal tradeoff. The board, queue, recent picks, rosters, news, runs, and exposure remain close supporting context, but do not compete equally for primary attention.

Responsive decision: desktop and tablet provide the full Draft Suite; phone widths provide a focused live companion with source health, clock status, three recommendations, queue, search, and fast manual entry. The full board, team matrix, scenario comparison, and detailed replay remain available through deliberate drill-down screens rather than compressed horizontal layouts.

## Fresh Engineering Review Decisions (2026-08-31)

The owner completed the Workstream 1 manual-draft dogfood gate and explicitly selected the complete original Draft Suite rather than a narrow autopick patch. Implementation is a structural rewrite around the planned module boundaries, not a second `/draft-v2` product: current tables, routes, IDs, and event history remain the compatibility boundary. A database reset is acceptable only as a recovery fallback; it is not the migration plan.

### Mock automation

- Canonical mock opponents use deterministic, team-aware `mock-opponent-v1` scoring: VOR, roster need, positional limits, scarcity, and Yahoo rank/ADP with stable tie-breaking. Each event records policy version, input hashes, and the decision components needed for exact replay.
- The server chooses and atomically commits exactly one next opponent pick. A visible browser loop invokes that action until the owner is on the clock, using sequence/idempotency protection so pause, reload, and multiple-tab races remain safe.
- Synthetic picks are accepted only for `kind=mock`, `source_mode=manual` sessions. The server rejects them for live or Yahoo-observed rooms. New mocks default to automatic opponents and expose pause plus an explicit manual-opponent mode.
- Canonical mock picks remain deterministic. Optional scenario simulations are separately seeded and stochastic, sampling around stored Yahoo rank/ADP dispersion and team needs without claiming exact future picks.

### Required ranking readiness

- A mock cannot start without a fresh immutable Yahoo ranking snapshot that can finish the configured draft: at least one mapped ranked player with a frozen projection for every configured pick, plus sufficient required-position coverage.
- Opening setup starts one single-flight authenticated Yahoo ranking scrape when no reusable snapshot exists. Setup shows progress and exact coverage, keeps Start disabled, and offers Retry after typed failures. A complete snapshot may be reused for 24 hours and refreshed explicitly.
- Yahoo HTML is the first ranking transport. It normalizes into a provider-neutral contract so a future verified Yahoo OAuth/API `draft_analysis` transport can replace the scraper without changing readiness, forecasting, or replay. Owner CSV/JSON import remains a manual recovery path.
- Login redirects, suspicious empty pages, partial pagination, malformed or duplicate ranks, identity gaps, and rate limits never create a ready snapshot.

### Computation, replay, and persistence

- Simulations are persisted asynchronous computation runs. `POST` returns the run immediately; the UI polls status. A bounded lifespan-managed single worker processes seeded playouts, while sequence/hash guards reject stale publication and restart marks unfinished work `interrupted`.
- Forecast status, source snapshot, freshness, coverage, calibration version, and per-candidate guidance are persisted with the immutable recommendation snapshot. Replay never recalculates them from current inputs.
- Owner-actionable snapshots persist compact scores/components for every eligible player; non-owner sequences retain the shortlist, hashes, provenance, and enhancement status. This preserves the entire at-time owner decision surface without multiplying full-board storage after every opponent pick.
- Waiver output is a maximum of five compatible add/drop pairs with projected gain, affected slot, and evidence freshness—not a renamed best-available list.
- Coaching keeps mock and live evidence in separate lanes. Each lane requires at least three completed sessions and a rule repeated in at least two before emitting a finding.
- Import previews are durable bounded staging records with TTL cleanup and atomic one-time commit; process restart cannot silently lose or indefinitely retain an active preview.

### Concurrency, performance, and rollout

- Every canonical mutation uses one per-session coordinator and a short SQLite `BEGIN IMMEDIATE` transaction. Yahoo/network I/O, scoring, and optional computation remain outside the lock.
- Immutable projection/ranking normalization, position indices, and replacement baselines use a bounded cache keyed by snapshot/config hash. Candidate scoring is linear in the eligible pool.
- The rewritten suite stays behind the existing suite flag while the validated room remains the parity oracle. Cutover occurs only after migration/parity, complete backend/frontend/browser/eval coverage, maximum-fixture performance gates, smoke checks, and rollback drills pass.
- The focused existing backend baseline is green: 20 Draft/migration/security tests passed on 2026-08-31. Frontend tests and builds run inside the application image because the host workspace does not provide Node.

## Vision

### 10x Check

The owner should feel as if a calm strategist is sitting beside them. Open Gridiron understands the league, remembers the plan, tracks the room, notices when the opportunity set changes, and explains whether to take a player now or risk waiting. The owner should not have to operate a spreadsheet, translate generic rankings, or mentally combine roster need, scarcity, news, ADP, and cross-league exposure while on the clock.

### Platonic Ideal

Before the draft, the owner imports or confirms league settings and prepares league-specific tiers, targets, fades, and strategy scenarios. During the draft, picks synchronize from Yahoo when reliable read access exists and require one fast action when manual entry is needed. When the owner is on the clock, the interface presents a short ranked set of serious choices, the evidence behind each choice, what is likely to remain at the next pick, and how each choice changes the plausible roster path. After the draft, a replay evaluates decisions using only information available at the time and turns recurring habits into specific preparation for the next league.

## Accepted Scope

### Pre-draft preparation

- Confirm league scoring, roster slots, league size, snake order, owner team, and owner team slot.
- Build league-specific rankings using value over replacement rather than raw rest-of-season value.
- Present explicit tiers, tier cliffs, positional scarcity, targets, fades, queue, and strategy notes.
- Support mock and scenario runs that use the same session and recommendation contracts as a live draft.
- Show data provenance, freshness, missing prerequisites, and unsupported assumptions before a session can be marked ready.

### Live draft assistant

- Treat Yahoo as a read-only source. Automatic polling may ship after the fixture and simulated-contract suite passes; retain freshness indicators and a fast manual mode because real Yahoo timeliness is not a release prerequisite.
- Represent the draft as a session with format, teams, order, rounds, current pick, ownership, and append-only events rather than deriving state from `picks.length`.
- Automatically derive who is on the clock; do not require the owner to type a team name for each pick.
- Provide a complete board with search, position filters, tiers, queue, recent picks, team rosters, and undo or correction for manual mistakes.
- Recompute recommendations after every accepted pick using league scoring, VOR, open roster slots, roster construction, positional scarcity, observed runs, player risk, and current evidence.
- Estimate whether a player will survive to the owner's next pick and show the source, freshness, confidence, and failure state of the forecast.
- Compare candidate picks through bounded multi-round scenarios. Clearly label these as plausible branches, not guaranteed future boards.
- Surface injury, role, suspension, contract, and depth-chart evidence with source links and timestamps. AI may explain verified inputs but may not invent or silently upgrade facts.
- Show cross-league exposure as information and optional strategy input. Never downgrade the best league-specific recommendation solely for diversification unless the owner explicitly enables that preference.
- Offer keyboard-first controls, a compact second-screen layout, queue promotion, on-deck alerts, and immediate manual-pick undo.

### Post-draft analysis

- Assess roster strengths, weaknesses, starting lineup, bench construction, positional risk, bye-week pressure, and immediate waiver priorities.
- Replay every pick against the board and recommendation snapshot that existed at that moment.
- Distinguish decision quality from later player outcomes; do not use hindsight injuries or season results to relabel a sound draft-day choice.
- Detect recurring strategy patterns across drafts and propose concrete changes for the next mock or live session.

## Product Boundaries

- Open Gridiron never submits a Yahoo draft pick and never presents a local action as if it did.
- Deterministic calculations produce rankings, scarcity, roster fit, simulations, exposure, and decision-quality inputs. AI explains those inputs and may answer comparisons, but it does not manufacture probabilities, ADP, injuries, or projections.
- Standard snake redrafts are the working first-release format.
- Keeper and salary-cap concepts may appear only as reserved format or cost fields where needed to avoid a closed data model. Their setup, recommendation logic, simulations, and live interfaces are not part of this release.
- Multi-user league hosting, commissioner controls, public draft rooms, and automated Yahoo writes are not in scope.

### Coupling and platform value

- Before: `api.py` writes mutable `DraftPick` rows and the page derives round/team assumptions from list length. Yahoo API and scraper behavior can disagree at persistence time.
- After: source adapters couple only to reconciliation, reconciliation couples only to the event service, and consumers couple to a versioned canonical-state contract. This justified coupling gives mocks, live drafts, correction, replay, exposure, and future providers one substrate.
- League scoring, identity mapping, freshness, evidence, secret storage, and provider analysis remain shared capabilities rather than Draft Room forks.
- The same immutable-snapshot and event-replay primitives can later support waiver-decision replay and trade-decision audits without adopting Draft Room UI or scoring rules.

### Live execution model

- Entering/resuming a live Draft Room triggers an immediate Yahoo catch-up, then a visibility-aware browser poll cadence. Closing every Draft Room pauses polling by design; reopening catches up before advice is called current.
- Multiple tabs may use `BroadcastChannel`/Web Locks to nominate one polling tab when supported, but correctness never depends on client leadership. The server's per-session single-flight guard coalesces or rejects overlapping polls, and provider keys keep retries idempotent.
- The sync endpoint performs bounded provider I/O, validates/reconciles, commits any accepted canonical events, and returns source status/proposals/current sequence. In shadow mode, observations do not mutate the board without owner resolution.
- After an event transaction commits, deterministic scoring runs outside the write lock in the serving FastAPI sync worker, persists snapshot N, and returns it when still current. A lost HTTP response is harmless because the event and snapshot are idempotently discoverable.
- Forecast refinement and simulation receive a serialized canonical board plus immutable input IDs. They run without a database connection in a single bounded worker process (`max_workers=1` for this private deployment). The application process alone verifies sequence/hash and persists a completed result.
- Simulation is user-triggered, not automatic after every pick. A newer sequence/request marks prior work canceled; cooperative cancellation stops between playout batches. Process restart marks any `running` optional computation `interrupted`, and the user can rerun it.
- A small `DraftComputationRun` record stores session, sequence, input hash, kind, request ID, status (`queued`, `running`, `complete`, `canceled`, `interrupted`, or `failed`), timestamps, duration, algorithm version, and sanitized error code. It is execution evidence, not a general job queue.
- No worker process receives Yahoo credentials, raw notes/news prose, or a database handle. Polling/provider I/O remains in the authenticated application process.

### Scaling and failure posture

| Condition | First pressure point | Planned response |
|-----------|----------------------|------------------|
| 10x current personal usage | Repeated scoring/simulation after rapid picks | Cache by session sequence and input hash; cancel superseded simulation; keep one in flight per session. |
| 100x or multi-owner deployment | In-process session locks and SQLite write serialization | Explicitly unsupported. Move locks/jobs and database together before claiming multi-process or multi-tenant support. |
| Yahoo outage or rate limit | Source freshness | Provisional manual mode with bounded retry and later append-only reconciliation. |
| Ranking/news/AI outage | Optional intelligence panels | Typed degraded state; deterministic recommendation continues when its required projection inputs remain valid. |
| Projection corruption | Core recommendation truth | Staged import and immutable versions; fail readiness or future advice rather than reuse an invalid current snapshot. |
| Process crash during mutation | Draft event write | One SQLite transaction commits event, sequence, and compatibility projection together; reload uses server state and idempotency key. |
| Database loss/corruption | Entire private instance | Existing rolling online backups and integrity-checked restore; no external source is treated as a complete substitute for local preferences/snapshots. |

Primary single points of failure are the local SQLite volume and single application process, both intentional for this private deployment. Yahoo, news, rankings, simulation, and AI are not allowed to become single points of failure for manual board tracking. Rollback preserves the append-only tables and legacy compatibility view; frontend can feature-flag back immediately, while backend rollback is read-only for draft mutations until the new event writer returns.

## Code Quality and Module Boundaries

Proposed backend feature package:

```text
backend/app/draft/
  router.py          # HTTP mapping only; no scoring or reconciliation branches
  schemas.py         # bounded request/response contracts and typed statuses
  models.py          # draft-only ORM tables, imported by application metadata
  session.py         # readiness and explicit state transitions
  events.py          # append transaction, idempotency, and invariants
  reducer.py         # pure event stream -> canonical board function
  reconciliation.py # Yahoo/manual precedence and identity conflicts
  rankings.py        # VOR, tiers, scarcity, runs, roster fit
  forecasting.py     # ranking snapshot gates and availability estimates
  simulation.py      # bounded, cancellable multi-turn scenarios
  imports.py         # validate-preview-commit workflow
  replay.py          # immutable at-the-time review and deterministic coaching rules
```

Proposed frontend feature package:

```text
frontend/src/features/draft/
  DraftRoute.tsx
  setup/
  live/
  replay/
  components/
  hooks/
  api.ts
  state.ts
  types.ts
```

- `backend/app/api.py` only includes the feature router; `frontend/src/App.tsx` only registers the route/navigation entry.
- The reducer and deterministic scoring functions accept explicit data and versions and perform no database, clock, network, random, or AI access. Callers inject time and seeded randomness where needed.
- Routers validate and translate. Transaction services enforce invariants. Adapters normalize external data. No class named only `DraftService` may accumulate all behaviors.
- Recommendation orchestration is a short pipeline of named stages rather than one method with provider, scoring, forecasting, simulation, and serialization branches. Any method exceeding five meaningful decision branches is split or expressed as an explicit table/state transition.
- Yahoo API and scraper adapters retain their transport-specific parsing but share provider-neutral normalized observations and one reconciliation policy. VOR, identity mapping, freshness, and evidence helpers reuse existing capabilities rather than copying their logic.
- The event model remains draft-specific. Do not introduce a generic application-wide event-sourcing framework, distributed queue, or microservice abstraction for hypothetical future scale.
- Names describe domain meaning (`expected_sequence`, `provider_confirmed`, `tier_urgency`, `replay_generation`) and all externally persisted enums and JSON shapes carry explicit versions.

## Key Dependencies and Risks

1. **Draft truth:** fixture tests cannot prove Yahoo's real latency, authentication-expiry, partial-result, or rate-limit behavior. Runtime freshness must expose lag immediately, the room must remain fully usable manually, and unproven observations cannot automatically replace canonical picks.
2. **Player pool quality:** VOR, tiers, and simulations are only useful when a complete immutable projection version and league scoring are populated, fresh, and bound to the session.
3. **Availability inputs:** pick forecasting needs a trustworthy ADP or opponent-ranking source. Missing or stale inputs produce `forecast unavailable`, never an invented percentage.
4. **Identity:** news, cross-league exposure, imports, and historical snapshots require every league/provider row to resolve to a canonical athlete; ambiguous name/team matching remains blocking rather than silent.
5. **Explainability:** recommendation snapshots must record inputs and versions so replay can reconstruct what was known without recomputing history from changed data.
6. **Manual correction:** the event model must support undo and correction without silently rewriting synchronized provider history.
7. **Scope control:** keeper and salary-cap UI and logic remain deferred even though the model preserves an extension path.

## Delivery Strategy: One Full-Suite Release

## Canonical Data Model

### `DraftSession`

- `id`, `league_id`, `kind` (`live` or `mock`), `format` (`snake` initially), `status`, `strategy_mode` (`adaptive` or `locked`), and versioned `strategy_config_json`.
- `team_count`, `round_count`, `owner_team_slot`, bound `projection_snapshot_id`, optional `ranking_snapshot_id`, `source_mode` (`manual`, `yahoo_scrape_shadow`, `yahoo_oauth_shadow`, `yahoo_scrape_authoritative`, or `yahoo_oauth_authoritative`), optional `authority_evidence_id`, `current_sequence`, and `replay_generation`. `owner_team_slot` is the single snake-order position; there is no separate `draft_slot` field.
- Immutable `scoring_snapshot_json`, `roster_slots_snapshot_json`, `config_version`, creation/start/completion timestamps, and optional provider league/draft keys.
- Keeper and salary-cap extension data may be stored only in nullable `format_config_json`; no first-release behavior reads it.

### `DraftTeam`

- Unique `(session_id, slot)` plus name, provider team key, and `is_owner`.
- Snake order is derived from slot, round, and team count; it is never inferred from free-text team names.

### `Athlete` and `AthleteAlias`

- `Athlete` is the cross-league football identity: `id`, canonical display name, active/retired status, created/updated timestamps, and optional manually verified metadata. Current NFL team is evidence, not identity, because players change teams.
- `AthleteAlias` stores `athlete_id`, provider, non-null namespace, non-null season/scope token, external ID, observed name/team/position, confidence, status (`pending`, `mapped`, or `ignored`), manual-verification flag, and audit timestamps.
- Unique `(provider, namespace, season_scope, external_id)` prevents one external identity from mapping twice. One athlete may have any number of aliases across Yahoo game/season namespaces, GSIS, nflverse, ranking vendors, imported owner IDs, and news sources.
- Each league-scoped `Player` references `athlete_id`. Ranking and projection snapshot rows, evidence matches, exposure aggregates, and replay snapshot candidate rows store `athlete_id` as the durable join plus their local/source row identifiers for provenance.
- Name/team/position may suggest a pending match but never auto-merge two athletes without a provider ID or explicit verified mapping. Team changes, duplicate names, suffixes, defense/team entities, and renamed providers have golden fixtures.
- Migrate each existing `IdentityMap` row into one athlete plus Yahoo/GSIS aliases. Backfill league players from exact verified aliases first, then show unresolved candidates in the staged identity workflow; do not activate cross-league exposure or historical joins until required rows are resolved.

### `DraftEvent`

- Append-only `sequence`, `type`, `overall_pick`, `round`, `team_slot`, `player_id`, `source`, `idempotency_key`, provider key/revision, observed time, recorded time, `reason`, versioned `metadata_json`, `early`, optional `supersedes_event_id`, and optional `recommendation_snapshot_id`.
- Event types: `session_started`, `source_mode_changed`, `input_snapshot_changed`, `pick_recorded`, `pick_reversed`, `pick_replaced`, `provider_confirmed`, `session_paused`, `session_resumed`, `session_completed`, `session_reopened`, and `session_abandoned`.
- A manual undo emits `pick_reversed`; a correction emits a reversal plus replacement. Provider events are immutable. Current board state is reduced from the event stream.
- Unique provider event keys make retries idempotent. Mutations require `expected_sequence`; a stale client receives `409 draft_conflict` plus current state.
- An owner-team `pick_recorded` request carries the recommendation snapshot the owner saw. Inside the event transaction, the server verifies that the snapshot belongs to the session, is the latest published snapshot for the current pre-pick sequence/input hash, and is ready. If absent or still computing, it returns retryable `advice_pending` without opening/committing a write. The accepted event stores `recommendation_snapshot_id`, making the pick-to-advice link atomic without running scoring inside the transaction.

### `DraftBoardPreference`

- Unique `(session_id, player_id)` with `queue_rank`, `target`, `fade`, `note`, and `updated_at`.
- Queue, targets, fades, and notes are server-persisted session data. Optimistic client edits carry an expected preference revision; reload always restores the latest acknowledged server version.

### `ProjectionSnapshot` and `ProjectionSnapshotRow`

- Snapshot fields: source/import type, original file/content hash, parser/schema version, retrieved/effective times, row count, canonical-athlete coverage, status, licensing/import metadata, created time, and a deterministic dataset hash.
- Each row stores `snapshot_id`, `athlete_id`, source row/alias provenance, versioned raw-stat projection fields when available, source-provided projected points/floor/ceiling/value/risk fields, position eligibility evidence, and a normalized row hash. Unique `(snapshot_id, athlete_id)` prevents duplicate active inputs.
- League-specific fantasy points and VOR are derived from snapshot rows plus the session scoring/roster snapshots. Recommendation snapshots store the bound projection ID, scoring/config versions, and derived inputs/results so the calculation can be reproduced.
- Legacy migration creates one `legacy-player-state` projection snapshot per league from current mutable `Player` values, clearly labels unavailable raw-stat provenance, and never claims more historical fidelity than exists.
- A session must bind a valid projection snapshot before `READY`. Changing it after `LIVE` is an explicit `input_snapshot_changed` action with `expected_sequence`; it creates no historical rewrite, increments the canonical sequence/input revision, and triggers a new recommendation snapshot for future picks.
- Mutable projection columns on `Player` may continue as a latest-value compatibility view during migration, but ranking/replay code is forbidden from reading them once a session has a bound snapshot. Remove or fully derive them only in a later reviewed migration.

### `DraftRankingSnapshot`

- Source, retrieval time, player identity, overall/position rank or ADP, uncertainty/dispersion, coverage, and licensing or import metadata.
- First automatic contract is an authenticated, allowlisted Yahoo player-page adapter with saved markup fixtures and provider-neutral normalization. Owner CSV/JSON remains a supported recovery/import contract. A future Yahoo OAuth/API adapter may replace the transport only after returned draft-analysis fields pass the same provenance, identity, freshness, and finishability gates.

### `DraftRecommendationSnapshot`

- Generated after every recommendation-changing canonical sequence and input revision, outside the event transaction. The current ready snapshot is a precondition for an owner-team pick; opponent picks do not require one.
- Stores session sequence, algorithm/config versions, input hash, projection/ranking/news snapshot IDs, candidate inputs and scores, forecast status, scenario summaries, created time, and source freshness.
- Replay reads this immutable snapshot. It never recomputes historical advice from current data.

### `DraftReconciliationConflict`, `DraftExternalIdentity`, and `YahooAuthorityEvidence`

- A conflict stores session, overall pick, status (`unresolved`, `resolved`, or `ignored`), canonical event, incoming provider/source payload, provider key/revision, detected sequence, created/resolved timestamps, resolution action, and resolving event IDs.
- A pending external identity is an `AthleteAlias` candidate with provider namespace/season, observed name/team/position, candidate athlete IDs, match evidence, and audit timestamps. An unmatched provider pick references it and cannot alter the canonical board while it remains pending.
- Authority evidence stores provider/transport/config versions, controlled-draft identifier, first/last observation times, consecutive-pick count, duplicate count, observation-delay distribution, partial-response checks, rate-limit responses, polling interval, pass/fail result, and generated time. A passing record meeting the 50-pick gate may authorize evidence-based promotion; an attended owner may instead explicitly confirm a feed already running in the matching approval mode.
- `GET /draft-sessions/{id}/conflicts` lists unresolved and historical conflicts. `POST /draft-sessions/{id}/conflicts/{conflict_id}/resolve` accepts `keep_canonical`, `accept_incoming`, `map_player_and_accept`, or `ignore_incoming` with `expected_sequence`; resolution appends the required confirmation/reversal/replacement events atomically.

## Session State Machine and Invariants

```text
SETUP --valid readiness--> READY --start--> LIVE --pause--> PAUSED
  |                         |                 ^             |
  +--> ABANDONED            +--> ABANDONED   +--resume-----+
                                              |
                                              +--> COMPLETE
                                              +--> ABANDONED
COMPLETE --explicit reopen with reason--> LIVE
```

- `SETUP -> READY` requires league scoring, roster slots, team count, round count, owner slot, complete unique team order, and at least one eligible projected player. Forecast data is optional and does not block readiness.
- Session configuration and league snapshots cannot change after `LIVE`. The owner must abandon and clone the session to use changed league settings.
- Picks are accepted only in `LIVE` or `PAUSED` correction mode. A new normal pick in `PAUSED`, `COMPLETE`, or `ABANDONED` is rejected.
- While `PAUSED`, the event API accepts only `pick_reversed`, `pick_replaced`, `provider_confirmed`, and explicit reconciliation-resolution events. It rejects a new unsuperseded `pick_recorded`; state actions may resume, complete, or abandon the session.
- At most one unreversed canonical pick exists per overall pick and per player in a session.
- Gaps and out-of-order picks are rejected during ordinary manual entry. Reconciliation may place a missing earlier provider pick only through the conflict workflow.
- Completion occurs when the configured number of picks is present, or through an explicit early-complete action carrying a reason. Early completion freezes the current board, writes `session_completed` with `early=true`, and generates a versioned partial replay report; it does not synthesize missing picks.
- Reopening requires an explicit reason and appends `session_reopened`, transitions `COMPLETE -> LIVE`, increments `replay_generation`, and marks the prior replay report superseded. Existing recommendation snapshots remain immutable; future owner turns create new snapshots under the new generation.

## Security and Threat Model

The Draft Suite introduces no public route. Every endpoint above lives on the existing protected router, uses the one configured owner, and inherits hosted-session authentication, mutation CSRF checks, API rate limiting, security headers, and HTTPS requirements. Loopback auth bypass remains limited to the existing local profile and does not change Draft Room behavior.

## Deterministic Recommendation Rules

- League scoring converts one versioned raw-stat projection snapshot into fantasy points.
- `VOR = projected fantasy points - projected points at the replacement rank` for the candidate's best eligible roster slot.
- Required starters across all teams establish position demand. Replacement is the first unassigned player beyond league-wide starting demand, never the final player inside that demand.
- Replacement allocation pseudocode: `(1)` create every required non-FLEX starter slot for all teams; `(2)` assign the highest-projected eligible unassigned player to each slot, choosing the assignment with the largest marginal points until all base slots are filled; `(3)` create every FLEX slot and greedily fill it from the remaining eligible players the same way; `(4)` for each roster-slot eligibility set, the replacement baseline is the highest-projected still-unassigned player eligible for that slot; `(5)` a candidate's baseline is the lowest baseline among slots the candidate can legally fill, and the candidate is counted once.`
- Worked FLEX fixture: two teams each require `RB`, `WR`, and `FLEX`. RB projections are `20, 16, 12, 7`; WR projections are `18, 15, 10, 6`. Base slots consume RB `20,16` and WR `18,15`; FLEX consumes RB `12` and WR `10`; the first players beyond starter demand are RB `7` and WR `6`. An RB projected at `16` therefore has RB-slot VOR `9`; a WR projected at `15` has WR-slot VOR `9`.
- Candidate scoring considers the top 60 currently available, roster-eligible players. For any component `x`, `normalize(x) = 0.5` when all 60 values are equal; otherwise `(x - min) / (max - min)` over that candidate set.
- Candidate score version 1 is `100 * (0.55 * normalized_vor + 0.20 * roster_need + 0.15 * tier_urgency + 0.10 * risk_adjustment)`. Every component and weight is returned to the client and stored with an algorithm version.
- Adaptive mode uses the objective score and bounded scenario utility to respond to the live board. Named strategies such as Zero RB or Hero RB are parallel scenario outputs and cannot alter the primary ranking unless the owner explicitly locks a versioned strategy configuration; locking or unlocking is recorded as a session event and explained in subsequent snapshots.
- Roster need is `1.0` for an empty required starter slot, `0.5` when only FLEX or bench capacity remains, and `0.0` when the candidate cannot improve a valid remaining slot. Bench-depth bonuses are excluded from version 1 rather than hidden in a weight.
- `risk_adjustment = 1 - clamp(player.risk, 0, 1)`.
- `next_eligible_vor` means the next lower-ranked available player who can legally fill at least one of the same roster-slot types as the candidate; it is not the next global player. Let `cliff_threshold = max(3.0 points, 10% of abs(current_vor))` and `vor_drop = current_vor - next_eligible_vor`. `tier_urgency = clamp(vor_drop / cliff_threshold, 0, 1)`. A tier cliff exists when `vor_drop >= cliff_threshold`; tiers are the contiguous same-slot-competition bands separated by those cliffs.
- A positional run alert fires when at least three of the last `max(6, ceil(team_count / 2))` picks share a position and that position's share is at least twice its share in the preceding full round.
- Scenario utility is measured in projected VOR points at the end of the second owner turn: starting-slot VOR plus `0.25 * bench VOR` minus `10 points * each still-empty required starter slot`. The candidate's scenario value is the mean utility across completed bounded playouts; fewer than 100 completed playouts produces `simulation.status=unavailable`.
- Decision quality is `chosen_score / best_available_score` when the best score is positive, otherwise `1.0` for an exact tie and `0.0` for a lower choice. A separate `scenario_regret` is best candidate mean scenario utility minus chosen mean scenario utility. Later outcomes never change either at-the-time value.
- Deterministic candidate order is composite score descending, scenario utility descending when available, VOR descending, risk ascending, ranking/ADP ascending when available, normalized player name ascending, then player ID ascending.
- Golden fixtures cover FLEX competition, multi-position eligibility, negative VOR, empty position pools, identical scores, missing projections, and an exact 12-team snake round reversal.

Worked scoring fixture: if the 60-player candidate set has VOR range `0..40`, a player with VOR `30`, an empty required starter slot, a `6` point drop to the next player against a `4` point cliff threshold, and risk `0.20` receives `normalized_vor=.75`, `roster_need=1`, `tier_urgency=1`, `risk_adjustment=.8`, and score `84.25`. An exact score tie follows the deterministic order above.

## Availability Forecast and Simulation Gates

- The ranking-source contract accepts licensed/provider adapters or owner-imported CSV/JSON containing player identity, ADP/rank, source time, and optional dispersion. Unauthorized page scraping is excluded.
- A forecast is `available` only when its ranking snapshot is no older than 48 hours and covers at least 90% of the current top 180 projected draftable players. Older data is `stale`; lower coverage is `unavailable`.
- Before forecast percentages ship, a time-ordered historical evaluation must beat an overall-rank-only baseline on Brier score and produce expected calibration error of at most `0.08`. Otherwise the UI shows ordinal timing guidance without a percentage.
- Per-pick simulation compares at most three owner candidates, advances through the next two owner turns, samples at most 500 bounded opponent playouts, prunes players outside the top 60 available by opponent utility, and targets local p95 latency under 400 ms. Timeout or missing inputs returns a deterministic single-pick result with `simulation.status=unavailable`.
- Yahoo live polling passes release verification through recorded full-draft API and scraper fixtures plus a deterministic simulated clock. The suite covers at least 50 consecutive observations, exact retries, gaps, corrections, OAuth-over-scraper precedence, manual overlap, unknown identities, timeout, expired authorization, `429 Retry-After`, malformed and suspiciously empty payloads, restart/resume, and reconnect reconciliation with zero duplicate canonical picks.
- The simulated poll loop must process each valid observation inside the local latency budget and honor configured/backoff intervals, but it cannot enable automatic authority because it does not measure Yahoo network observation delay, partial-result behavior, or real rate-limit tolerance. Polling therefore ships in shadow-confirmation mode with runtime last-success age, source status, and provisional-manual entry.
- Evidence-based automatic authority requires an owner-controlled Yahoo mock/live rehearsal with at least 50 consecutive observed picks, zero duplicates, p95 observation delay no greater than 5 seconds, no unsafe partial-response replacement, and no rate-limit response at the chosen polling interval. Store the evidence summary/version. During an attended draft, the owner may instead explicitly confirm the active approval feed. Enabling authority is always an explicit session action, never an automatic mid-draft transition.
- Forecast evaluation pairs owner-imported or licensed pre-draft ranking snapshots with archived Yahoo draft-result sequences already stored by Open Gridiron. Phase 2 requires at least 10 complete drafts and 1,000 observed picks for percentage calibration; with less data, the product may show ordinal `likely now`, `borderline`, or `likely later` guidance but no probability. Synthetic fixtures verify code only and never satisfy calibration.

## Yahoo Reconciliation Policy

All Yahoo API and scraper records enter one reconciliation service:

| Situation | Action |
|-----------|--------|
| Provider pick exactly matches a manual pick | In either mode, emit `provider_confirmed`; link provider key without changing the board. |
| Shadow source supplies a missing pick | Store an ordered reconciliation proposal without changing the board. The owner may accept one or a contiguous batch with `expected_sequence`; acceptance appends normal provider `pick_recorded` events and recomputes downstream advice. |
| Shadow source conflicts with a manual player/team or corrects a prior pick | Store an unresolved conflict/proposal with before/after values. Require `keep_canonical`, `accept_incoming`, or ordered batch resolution; no automatic reversal occurs. |
| Evidence-gated authoritative source supplies a missing pick | Append provider `pick_recorded`, including an earlier gap through the reconciliation transaction, then recompute downstream order and advice. |
| Evidence-gated authoritative source conflicts or corrects | Atomically append reversal and provider replacement events, mark the superseded event, invalidate stale advice, and show a persistent correction notice. |
| OAuth and scraper disagree | OAuth observation wins when configured; otherwise the configured scraper observation wins. The losing observation is retained in audit. The session's shadow/authoritative mode still determines whether the winning observation is proposed or applied. |
| Unknown or unmatched provider player | Create a pending external identity and proposal without altering the canonical board. Mapping plus explicit acceptance is required in shadow mode; evidence-gated authoritative mode may apply only after mapping, never via an ambiguous placeholder. |
| Retry or overlapping manual/sync mutation | Idempotency key plus `expected_sequence`; losing caller receives `409` and reloads canonical state. |

The current OAuth insert-only behavior and scraper overwrite behavior are removed from direct persistence. Both call the shared policy. A session begins in shadow mode. Switching between manual, shadow, and evidence-gated authority is an explicit state-changing action with a reason and evidence reference where required; it affects future observations and never reverses provider events already accepted.

Conflict tests cover persistence across reload/restart, concurrent duplicate detection, OAuth-over-scraper precedence, exact auto-confirmation, shadow proposal/keep/accept/batch flows, rejection of authority without passing evidence, evidence-gated automatic replacement, stale visible-recommendation rejection, list filtering, every identity-resolution action, mapped identity application, ignored identity, and the rule that `COMPLETE` cannot coexist with a blocking unresolved identity.

## Interaction and Failure Rules

| Case | Required behavior |
|------|-------------------|
| Double-click manual pick | One idempotency key creates one event; button disables while pending. |
| Reload during mutation | Server event is canonical; reload resumes from latest sequence and reports whether the pending idempotency key committed. |
| Navigate away during live draft | Session continues server-side. Queue/preferences are server-persisted; navigation warns while an optimistic edit is unacknowledged and reload restores the last acknowledged preference revision. |
| Duplicate player or overall pick | Reject with `409 duplicate_pick` and return the conflicting canonical event. |
| Pick gap or wrong team slot | Reject with `422 invalid_draft_order`; never silently renumber. |
| Projection or ranking refresh during draft | Create/choose a new immutable snapshot and append `input_snapshot_changed`; it affects future recommendations only and stored prior snapshots remain immutable. |
| News source fails | Keep deterministic rankings, mark news `failed`, and show last successful source time. |
| Simulation exceeds budget | Cancel simulation result and retain deterministic recommendations. |
| Yahoo adds picks while manual entry is active | Serialize by session; exact matches confirm. Shadow missing/conflicting observations wait for approval; evidence-gated authority may apply through reconciliation. |
| Yahoo is unavailable during a live draft | Keep accepting visibly provisional manual events and recomputing advice. Show the last successful sync time and provider error state; retry with bounded backoff, then reconcile against Yahoo on recovery. |
| Recommendation changes before `Record pick` arrives | Reject with `409 stale_recommendation`, return canonical state, refresh, and preserve the intended player highlight; require fresh confirmation. |
| Session completes or reopens | Freeze or invalidate the appropriate replay version and state this visibly. |

## Data Flow and Interaction Edge Cases

### Setup and staged imports

```text
FILE/SETUP -> SIZE+TYPE VALIDATION -> PARSE+IDENTITY MATCH -> STAGED PREVIEW -> EXPLICIT COMMIT -> IMMUTABLE SNAPSHOTS
    |                 |                       |                    |                  |
 nil/empty       wrong type/limits      malformed/duplicate   expired/changed   transaction conflict
 reject 422      reject 413/422         show blocking rows    return 409        roll back; no snapshot
```

An empty file is not a valid zero-player snapshot. Warnings may be accepted; blocking errors, unresolved identities, insufficient projection coverage, changed content hashes, and cross-league preview IDs may not. Preview and commit receive integration tests for UTF-8 edge cases, formula-like cells, non-finite numbers, duplicate identities, expiration, double-submit, and atomic rollback.

### Manual live pick

```text
CLICK/KEY -> CLIENT PENDING GUARD -> EXPECTED SEQUENCE+SNAPSHOT -> EVENT TRANSACTION -> REDUCE BOARD -> NEW ADVICE
    |                |                         |                       |                 |

```

The UI disables a pending action, but correctness depends on server idempotency, sequence, and snapshot-readiness checks. `advice_pending` keeps the intent highlighted and retries only while the same sequence remains current. A stale recommendation never records automatically: refresh preserves the intended player highlight and requires one fresh confirmation. A player taken during refresh becomes unavailable and cannot be confirmed.

### Yahoo synchronization and recovery

```text
POLL/REFRESH -> FIXED-HOST FETCH -> VALIDATE PAYLOAD -> RECONCILE OBSERVATION -> MODE DECISION -> BOARD/ADVICE
      |               |                  |                       |                  |

Provider absence never means an empty draft. ### Recommendation and simulation

```text
CANONICAL BOARD -> LOAD VERSIONED INPUTS -> SCORE TOP 60 -> OPTIONAL FORECAST/SIM -> SNAPSHOT -> RESPONSE

No eligible candidate returns a named terminal or configuration finding rather than an empty successful card. Simulation cancellation, randomness, and time are bounded and seeded in tests; deterministic scoring and reason strings always remain independently available.

### Replay and coaching

```text

## SQLite Concurrency and Idempotency

- Database constraints enforce unique `(session_id, sequence)` and unique `(session_id, idempotency_key)` for all draft events, plus the provider-key uniqueness described above.
- Because Open Gridiron intentionally runs one application process, each mutation acquires an in-process lock keyed by session ID, starts one SQLite `BEGIN IMMEDIATE` transaction, re-reads `current_sequence`, checks `expected_sequence`, appends the event, updates the session sequence and compatibility projection, and commits before releasing the lock.
- A uniqueness race returns the already-committed idempotent result or `409 draft_conflict`; it never retries with a silently incremented sequence.
- Multi-process deployment is unsupported until the lock is replaced with a database-backed or distributed equivalent.

## Legacy Cutover and Rollback

1. The migration creates new tables and imports existing `DraftPick` rows idempotently into one legacy session per league. It preserves the old table as `draft_picks_legacy`; no imported row is deleted.
2. After cutover, a read-only SQL view named `draft_picks` exposes the current canonical picks from the designated default live session using the legacy columns. The new backend writes only events; it does not dual-write a second authority.
3. Existing `GET /leagues/{league_id}/draft` reads the compatibility view. Existing POST requests in the new backend are marked deprecated and route through the session event service. Direct writes to the view fail visibly, so a rolled-back old backend can inspect current state but cannot create divergent legacy picks.
4. A feature flag switches the frontend between old and session screens during Phase 1 verification. Frontend rollback is safe. Full backend rollback is explicitly read-only for draft mutations; operators take an online backup first and return to the new backend for writes.
5. If an emergency old-backend write must be recovered, the operator exports it into `draft_picks_legacy`, restores the new backend, and runs an idempotent delta-import command that produces normal events plus conflicts; the view is never made writable.
6. Remove the legacy adapter, renamed table, and compatibility view only after one full draft season, 30 consecutive days without rollback, zero legacy-client calls in logs, and an exported backup. Removal is a separate reviewed migration.

## Phase 2 and 3 Output Contracts

- **Cross-league exposure:** for each canonical `athlete_id`, return `rostered_league_count / active_or_completed_league_count`, the league IDs, contributing league-player IDs/aliases, and an optional league-importance-weighted exposure using owner-supplied weights that default to equal. Pending/unresolved aliases are excluded visibly rather than name-merged. Exposure is informational unless the owner explicitly enables a versioned strategy rule.
- **Immediate waiver priorities:** after completion, compare each rostered bench or weak starter against currently unrostered players using the same VOR and roster-fit functions. Return at most five upgrade pairs with projected gain, affected slot, evidence freshness, and no transaction automation.
- **Pattern detection:** emit only versioned deterministic rule IDs with evidence. Initial rules are `repeated_tier_reach` when the choice is at least two tiers below the best available without a higher roster-need score, `late_required_slot` when the owner fills a required position after at least 75% of league teams, and `high_exposure` when a player appears in more than 50% of the owner's active/completed leagues.
- **Coaching:** each finding names the sessions and picks that triggered it, the measurable draft behavior, and one next-mock exercise. AI may rewrite the explanation but cannot add a finding. Pattern coaching requires at least three completed sessions and the rule must trigger in at least two; otherwise the replay says `insufficient_history`.

| Migration/rollback | Migration + integration | Legacy picks import once and compatibility reads match | Failed migration rolls back without deletion | Rerun, partial old data, old reader/new writer coexistence, emergency delta import |
| Full-room journey | Browser E2E | Automatic 12-team mock and keyboard-only live fixture run from setup through replay | Optional services fail while manual live room remains usable; automatic mock stops safely on required-input failure | Ranking sync/reuse/retry, two-tab auto loop, reload/navigation on every turn, Yahoo outage/recovery, rapid corrections, desktop/tablet/mobile |

The first E2E milestone is intentionally smaller than the final 12-team journey: a deterministic four-team, three-round fixture with known projections and aliases. It proves the harness and every state boundary quickly before scaling the same helpers to the maximum/full-room fixtures.

The fixture API is a FastAPI router injected only by the test application factory when `APP_ENV=test`; production startup/build cannot import or register it, and a guard test enumerates production routes to prove absence. It supports deterministic session creation, clock advancement, provider-observation injection, typed failure injection, process/reload checkpoints, and state inspection without bypassing the real event/reconciliation/recommendation services. Playwright uses existing `frontend/playwright.config.ts` and `@playwright/test`, role/label selectors, fixed test clocks, and no arbitrary sleeps.

The 2 a.m. Friday confidence test is the full-room journey plus a database restart at three deterministic sequence points and a byte-for-byte replay snapshot comparison. The hostile QA test races manual entry, Yahoo correction, stale recommendation confirmation, preference reorder, and page reload on the same owner turn. The chaos test injects Yahoo timeout/401/429/malformed responses, news and AI failure, simulation timeout, and process interruption while proving that committed event history remains valid and the draft can finish manually.

The test pyramid remains unit-heavy: pure reducer/scoring/state/property tests, fewer transaction/adapter integrations, and a small set of high-value browser journeys. Time is injected, simulation randomness is seeded, external services use recorded contracts, and assertions wait on named states rather than sleeps. No `CLAUDE.md` prompt-test guidance exists in this workspace; the new draft-explanation evaluation must therefore extend the existing provider schema tests with grounding, refusal, malformed output, and adversarial dossier cases, using deterministic recommendation output as the invariant baseline.

## Performance Review

### Critical request path

```text
append event transaction (<50 ms p95 target)
             |
             +--> return canonical sequence/board delta
             |
             +--> deterministic score outside transaction (<150 ms p95)
                         |
                         +--> cache immutable result by sequence + input hash
                         +--> start/replace forecast and simulation enhancement
                                      |
                                      +--> publish only if sequence/hash still current
```

The write lock covers only invariant checks and event/session/compatibility persistence. It never covers Yahoo I/O, news, AI, ranking imports, scoring, forecast, simulation, or replay generation. If the process exits after sequence N commits but before snapshot N is ready, the next recommendation request restarts deterministic generation from canonical state; an owner-pick request returns `advice_pending` until that snapshot persists. No recovery event is required.

### Query and index plan

- Unique/indexed event access: `(session_id, sequence)`, `(session_id, idempotency_key)`, normalized provider key/revision, and active pick lookups by `(session_id, player_id)` and `(session_id, overall_pick)`.
- Session access: `(league_id, status, updated_at)`; team access: unique `(session_id, slot)` and provider team key.
- Snapshots: `(session_id, sequence, replay_generation)`, input hash, unique `(projection_snapshot_id, athlete_id)` and `(ranking_snapshot_id, athlete_id)` plus local row provenance; preferences: unique `(session_id, player_id)` plus queue rank.
- Identity/reconciliation: unique `(provider, namespace, season_scope, external_id)` aliases, indexed `athlete_id`, and `(session_id, status, created_at)` proposals/conflicts.
- Board loading uses bounded eager queries for teams, active reduced picks, preferences, current ranking/projection rows, and only the news/evidence required for returned candidates. No per-player ORM traversal or serialized lazy load is allowed.
- Replay pages fetch recommendation snapshots and chosen events in ordered batches and paginate detailed pick evidence; cross-league exposure aggregates canonical athlete IDs in one grouped query rather than one query per player or league.

### Cache and memory bounds

- Cache deterministic board/recommendation output by `session_id + sequence + algorithm/config/input hashes`. Because the key is immutable, invalidation means publishing a new key; retain only the latest three sequences per active session in memory.
- Cache normalized ranking/projection inputs, position indices, and identity maps by immutable snapshot ID plus precomputed replacement baselines by scoring/roster/input hash. Use a bounded in-process LRU; candidate scoring must remain linear in the eligible pool and cache eviction must never change output.
- Persist full eligible-player score rows only for owner-actionable snapshots. Non-owner snapshots keep the shortlist and provenance/enhancement state, avoiding hundreds of redundant full-board payloads in a deep automatic mock.
- A live session is bounded to 480 canonical picks for the supported 16-team/30-round maximum, 500 returned draftable players, three primary simulation candidates, 500 playouts each, and ten visible recommendation candidates.
- Store event/replay history in SQLite, not in an ever-growing process list. Imported file bytes and staged parse structures are released after commit/expiration.
- Yahoo/news HTTP clients reuse bounded connection pools. Draft work does not add dynamic scheduler jobs: browser requests drive sync, the application enforces one sync in flight per session, and one isolated worker process handles optional computation without an independent database connection per candidate or playout.

### Slow-path budgets on the reference environment

| Path | p95 | p99/hard bound | Degradation |
|------|-----|----------------|-------------|
| Event append and canonical delta | 50 ms | 100 ms | Busy retry twice, then visible failure; no optimistic commit |
| Board plus deterministic recommendation | 150 ms | 250 ms | Recompute from canonical inputs; block only if required projections are invalid |
| Two-owner-turn simulation | 400 ms | 750 ms / 800 ms cancel | Keep deterministic recommendation and mark simulation unavailable |
| Yahoo fixture normalization/reconciliation for one poll | 150 ms | 300 ms | Backoff/provider state; manual mode remains available |
| 480-pick replay summary from warm snapshots | 500 ms | 1 s | Paginate details; generation may remain visibly pending |
| 10,000-row import preview | 1 s | 2 s | Reject over bounds; no snapshot mutation |

Performance tests record query counts, peak memory, cold/warm cache, and hardware/runtime metadata as well as time. They measure board plus deterministic recommendations, one automatic-opponent pick, ranking normalization, fixture-based Yahoo reconciliation, asynchronous simulation completion, and replay. The board path fails if query count grows with returned player count, replay fails if query count grows per pick, and agreed p95 budgets gate CI. Stress tests use simultaneous sync, automatic/manual retry, board reads, preference updates, and cancellable simulations against the maximum supported fixture; SQLite busy behavior and connection reuse are part of the acceptance result.

## Observability and Debuggability Review

Every request, job, and derived output carries a `request_id`; draft work additionally carries `session_id`, starting/current sequence, input hash, algorithm version, and job attempt. Structured entry, significant-branch, and completion logs use allowlisted fields. They never contain secrets, authorization material, raw source bodies, raw imported rows, or owner/news prose.

### Day-one metrics and dashboard

| Signal | Metric/panel | Broken threshold or interpretation |
|--------|--------------|------------------------------------|
| Canonical writes | append count, p50/p95/p99 latency, `409`/`422`, DB-busy retries | Any invariant violation or sustained p95 over 50 ms |
| Yahoo health | browser poll heartbeats, sync attempts/results by typed status, single-flight coalesces, last-success age, proposed/applied/confirmed counts, backoff state | Visible live room exceeds `max(2 × poll interval, 15 seconds)` without success, or repeated auth/payload failures |
| Reconciliation | conflicts by source/result, unresolved identity count and age | Any blocking identity while owner is on deck/on clock; repeated source disagreement |
| Advice | deterministic latency, cache hit rate, status, candidate count, input age | Empty ready result, p95 over 150 ms, stale required input, or output for a superseded sequence |
| Forecast/simulation | available/stale/unavailable rate, duration, cancel/timeout count | Sudden availability collapse or simulation p95 over 400 ms |
| Evidence/AI | news freshness/failure, explanation success/fallback/schema/grounding failures | Deterministic advice continues; alert only on sustained failure, never page the draft history path |
| Replay | build duration/status, snapshot/hash integrity failures, superseded generations | Any integrity failure is high severity and blocks affected replay |
| Imports | preview/commit count, blocking-error categories, coverage, size/duration | Partial activation is an invariant violation; preview p99 over 2 seconds |
| UI journey | client-visible stale/conflict/degraded states and recovery completion | Repeated recovery loop, aging shadow proposals, or unacknowledged evidence-gated correction |

The in-app draft health strip shows source status, last successful Yahoo observation, projection/ranking/news ages, current sequence, and whether deterministic/forecast/simulation outputs are current. The operational dashboard adds latency, errors, conflict/identity counts, job status, and integrity results without requiring log inspection.

### Capability isolation

- Operator settings/env flags: `draft_yahoo_polling_enabled`, `draft_forecasting_enabled`, `draft_simulation_enabled`, and `draft_ai_explanations_enabled`. They default on only when the global suite is enabled, are never exposed as ordinary cockpit preferences, and appear in health/diagnostics.
- Each adapter/service checks its switch before starting work and returns `unavailable: disabled_by_operator` without queuing, fetching, or partially publishing output.
- Circuit breakers use typed failures and bounded rolling windows, not catch-all exceptions: Yahoo auth/payload/rate-limit failure, repeated forecast computation failure, repeated simulation timeout/worker exit, and repeated AI schema/grounding failure. Opening a circuit cancels that capability's in-flight optional work, records reason/time, and leaves deterministic advice/manual events intact.
- Automatic cooldown probes may close transient source/worker circuits only after a successful health operation. Authorization and integrity failures require explicit operator action. Every open/close/reset is audit logged and visible in the operational dashboard.
- Tests cover each switch off at startup and mid-session, each breaker threshold/probe/reset, process restart with an open breaker, diagnostics redaction, and the invariant that event append/manual completion still works with all four optional capabilities disabled.

### Redacted diagnostics and audit

`GET /api/v1/draft-sessions/{session_id}/diagnostics` is owner-authenticated, CSRF-free because it is read-only, rate-limited, and returns a downloadable versioned JSON bundle containing:

- session configuration with private free text removed;
- ordered event metadata, provenance, sequence, supersession, and idempotency fingerprints—not raw idempotency tokens;
- recommendation input/output hashes, deterministic components, algorithm versions, and optional-service statuses;
- source freshness and sanitized provider status codes;
- reconciliation decisions and identity status without raw incoming bodies;
- request/job correlation IDs, durations, retry counts, cache results, and typed error codes;
- replay integrity results and application/schema versions.

The export is generated from existing durable records and a bounded recent metric window; it does not create a new long-lived copy server-side. A diagnostic-bundle schema fixture prevents accidental addition of secrets or prose, and a secret-scanner test covers representative Yahoo, AI-key, cookie, note, and news values.

### Operator tools and runbooks

- `draft doctor SESSION_ID` verifies sequence continuity, reducer invariants, active-pick uniqueness, snapshot references/hashes, pending identities, current source state, and replay generations without mutating data.
- `draft reconcile-preview SESSION_ID FIXTURE_OR_FETCH_ID` shows the events a provider observation would append but cannot apply them; normal authenticated reconciliation remains the only writer.
- `draft replay-verify SESSION_ID` compares persisted event/snapshot hashes and reports the smallest affected sequence.
- Runbooks cover Yahoo timeout/auth/rate-limit/payload failures, stuck provisional mode, unresolved identity on the clock, SQLite busy/corruption, missing projection snapshot, stale enhancement job, replay integrity failure, and safe frontend rollback.
- High-severity integrity failures create a persistent in-app operator alert and structured error. Source outages create the live health banner and only escalate after sustained failure; they do not wake or disable the manual room.

Three weeks after a reported issue, the durable event/recommendation history plus diagnostic bundle must answer: what board sequence the owner saw, what inputs and versions were used, why each candidate scored as it did, what Yahoo observations arrived and won, which optional services failed, and whether a stale client action was rejected. If any answer requires reconstructing from current projections or unredacted raw logs, observability is incomplete.

## Deployment and Rollout Review

```text
BACKUP -> ADDITIVE SCHEMA -> DEPLOY FLAG OFF -> LEGACY IMPORT/PARITY -> FULL TEST+SMOKE
                                                                     |
                                                                     v
                          ENABLE FULL SUITE <- ATOMIC VIEW SWAP <- NO-DRAFT GATE
                                  |
                                  v
                          METRICS + DOCTOR + BACKUP
                                  |
                      +-----------+-----------+
                      | healthy               | incident
                      v                       v
                 keep enabled          rollback flow below
```

### Migration and activation order

1. Take and integrity-check an online backup. Record application, schema, parser, reducer, and algorithm versions.
2. Apply an additive migration that creates draft session/event/team/preference/snapshot/conflict/identity/import-staging tables and indexes. Leave the existing `draft_picks` table and old page active.
3. Deploy code with `draft_suite_enabled=false` and all internal Draft capabilities disabled. The hidden Draft UI emits no polling heartbeat; reject Draft sync/computation requests while disabled except operator-only import/verification commands.
4. Import legacy rows idempotently into designated legacy sessions, reduce them, and compare sequence, player, team, round, and overall-pick results against the old table. Any mismatch blocks activation.
5. Run migration, maximum-fixture, Yahoo-contract, manual-room, replay-integrity, diagnostics-redaction, and browser smoke checks in the production-shaped environment.
6. Enter a brief no-draft maintenance gate, verify no legacy mutation is in flight, rename `draft_picks` to `draft_picks_legacy`, create the read-only compatibility view in the same transaction, and re-run parity checks.
7. Enable the single suite flag and verified capability switches. Start the bounded optional-computation worker, activate per-session sync guards, and expose the complete setup/live/post-draft experience together; browser heartbeats begin only for visible live rooms.
8. Keep the fallback and compatibility layer through one full draft season, at least 30 consecutive healthy days, and zero legacy-client calls before a separately reviewed cleanup migration.

All new columns are nullable or have deterministic server defaults until the new writer is active. Large legacy import/reduction work occurs outside schema-change transactions and checkpoints progress idempotently. The cutover transaction contains only the validated rename/view swap; its lock time is measured on a production-size copy before release.

### Rollback

```text
INCIDENT
   |
   v
disable suite flag + reject new sync work + cancel optional runs
   |
   v
preserve event/snapshot tables -> legacy read-only page available?
                                      | yes                 | no / DB integrity failure
                                      v                     v
                              diagnose with doctor     restore verified backup
                                      |                     |
                                      +----------+----------+
                                                 v
                                  fix/redeploy NEW event writer
                                                 |
                                      parity + integrity checks pass?
                                           | yes       | no
                                           v           +-> remain read-only, continue incident
                                  re-enable full suite
```

1. Disable `draft_suite_enabled`, reject new browser-driven sync requests, and cancel/mark interrupted optional computation runs.
2. Preserve new tables and event history; do not reverse or delete migrations during incident response.
3. Serve the legacy page in read-only mode through the compatibility view, with a clear maintenance notice for draft mutations.
4. Run `draft doctor` and export the redacted diagnostic bundle for affected sessions.
5. Fix or redeploy the new backend, re-run parity/integrity checks, and re-enable the suite. If database integrity itself failed, restore the verified backup and re-import any recoverable provider observations through normal reconciliation.

Rollback target is under five minutes for the UI/worker flag and under thirty minutes to diagnose, restore a known-good new backend, and resume writes. An old backend is never allowed to write through the compatibility view because that would create a second authority.

| Window | Checks |
|--------|--------|
| Before enable | Backup verified; schema/import parity; all test gates; no blocking identities; feature flag and worker state confirmed. |
| First 5 minutes | Create/open test session, load board/advice, append and reverse one fixture/manual event, verify sequence/cache/metrics, confirm diagnostics contains no secrets. |
| First hour | Watch append latency/conflicts, SQLite busy rate, Yahoo typed statuses, source age, cache hit rate, enhancement cancellation, capability-switch/circuit state, and replay integrity. |

Automated post-deploy smoke tests operate only on a clearly named disposable verification session and use API-created fixture events; they never connect to or mutate a real Yahoo draft. Cleanup is idempotent and cannot target active or non-verification sessions. Environment parity requires the same Python/Node/SQLite versions, WAL mode, one-process topology, HTTPS/auth profile, scheduler configuration, maximum database fixture, and feature-flag behavior used by production.

## Long-Term Trajectory Review

### Data lifecycle

- Completed, early-completed, abandoned, and superseded draft generations remain until explicit owner deletion so replay and audit remain reproducible. Abandoned sessions are excluded from coaching by default but can be inspected.
- The delete screen names counts for events, recommendation snapshots, preferences, conflicts, identities, replay generations, and coaching findings that will disappear. It explains which aggregate patterns will be recomputed and requires typing the session name for a completed draft.
- Deletion cascades session-owned records in one transaction, then runs reducer/reference integrity checks. League-wide projection/ranking snapshots, stable identities, evidence, and imports referenced by other sessions are retained; unreferenced temporary previews continue to expire automatically.
- Active/live sessions cannot be deleted. They must first be explicitly abandoned with a reason. Deletion appends an operator audit record outside the deleted session containing only session ID, owner action time, reason, and result—not picks or notes.
- Existing rolling backups may contain a deleted session until they expire under the existing backup policy. The UI says this before confirmation; deletion does not rewrite historical backups.

### Debt, reversibility, and ownership

| Concern | Assessment | Control |
|---------|------------|---------|
| Event/snapshot storage growth | Low for one owner; intentional cost of audit/replay | Retain by owner choice, bound optional payloads, expose counts/size, explicit deletion |
| SQLite/in-process locking | Known topology debt if usage expands | Document single-process invariant; do not claim scale beyond it; migration trigger defined at multi-process/multi-owner work |
| Provider fixture drift | Medium because real Yahoo dress rehearsal was declined as a gate | Version recorded fixtures, runtime source metrics, typed degraded state, adapter contract isolation |
| Algorithm evolution | High risk to historical interpretation without versions | Immutable inputs/output, named algorithm/config versions, no historical recomputation |
| AI/provider churn | Low core risk | Optional boundary, shared provider contract, deterministic fallback and evals |
| Feature breadth | Medium maintenance burden from full-suite release | Cohesive module, workstream gates, explicit unsupported formats, owner-facing `unavailable` states |

Overall reversibility is **4/5**. The UI, jobs, and integrations are flag-reversible; new tables are additive and history is preserved. The one-way element is choosing append-only canonical state after activation—returning to legacy mutable writes would deliberately forfeit audit correctness, so rollback remains read-only rather than pretending it is symmetric.

Ownership documentation includes the architecture diagram, event catalog/invariants, reducer contract, source precedence table, deterministic formula versions, snapshot/replay guarantees, error map, operational dashboard/runbooks, fixture provenance, migration/rollback steps, and a “new engineer in 12 months” walkthrough from one pick observation to replay. Persistent enums, JSON payloads, diagnostics, and import formats are versioned and have compatibility tests.

### Platform path after this release

1. **Stabilize and calibrate:** use retained drafts to measure forecast calibration, runtime Yahoo behavior, decision latency, and coaching-rule precision. Change weights or rules only through new versions and time-ordered evaluation.
2. **Extend supported formats deliberately:** keeper and salary-cap drafts remain the next major format candidates. Their costs, nominations, inflation, and retention rules require separate product and algorithm review; reserved format fields do not imply support.
3. **Reuse decision-history primitives:** immutable input/recommendation snapshots, deterministic reasons, diagnostic export, and no-hindsight replay can support waiver and trade decision audits without generalizing the draft event model itself.
4. **Improve personal strategy:** with sufficient retained history, add evidence-backed owner tendencies, calibration by round/position, and targeted mock exercises. Never infer a pattern below the existing evidence threshold or from later player outcomes.

The architecture avoids path dependence toward a hosted multi-user draft platform. If sharing, multi-process deployment, or league hosting is ever proposed, it requires explicit tenant ownership, authorization, database/lock/job migration, privacy/retention controls, and a new security review before implementation.

The 12-month ideal is a trusted personal draft strategist that prepares league-specific plans, tracks the room, makes the next-pick tradeoff obvious, and teaches from prior decisions without hindsight. This plan reaches that ideal for standard snake redrafts if its full release gates pass.

### Responsive intention

- Desktop (`>=1200px`): full cockpit, board, and context rail visible without horizontal page scrolling.
- Tablet (`768–1199px`): three choices remain first; board and context use resizable/stacked regions with the queue pinned as a drawer.
- Phone (`<768px`): pinned health/clock strip, swipe-free vertical candidate stack, queue/search/manual entry, recent picks, and explicit drill-down routes. No wide table is squeezed or made dependent on horizontal scrolling.
- Mobile correction, identity resolution, imports, detailed scenario comparison, team matrix, and replay evidence use full-screen sheets/pages with a clear return to the live sequence.

### Accessibility and interaction craft

- Every action is keyboard reachable with visible focus. Define shortcuts for search, queue movement, record, undo, and candidate navigation, but never make shortcuts the only path.
- Announce on-clock changes, accepted/rejected picks, new shadow proposals, evidence-gated corrections, and source degradation through polite/assertive live regions appropriate to urgency. Do not repeatedly announce polling.
- Color never carries status alone; pair it with text/icon/age. Preserve at least WCAG AA contrast and 44 px phone targets.
- A stale-action refresh returns focus to the highlighted candidate or a precise unavailable message. Dialogs/sheets trap and restore focus; virtualized rows preserve logical keyboard position.
- Reduced-motion disables celebratory or movement transitions. Score changes use brief, localized emphasis instead of resorting the page without explanation.

The emotional arc is: **prepared** during readiness, **calm and decisive** on the clock, **in control** during source trouble or correction, and **curious rather than judged** in replay. Coaching language names a repeated behavior and practice exercise, not a grade on the person.

Avoid generic dashboard card soup, decorative gauges, opaque “AI confidence,” and equal-weight panels. Small high-value touches include a persistent “read-only, never submits to Yahoo” label; exact next-owner-pick countdown; one-key queue promotion; before/after correction toast; source-age text beside every optional insight; and an at-time badge throughout replay.

Before implementation, run `/plan-design-review` for a deeper interaction/layout pass. After implementation, run `/design-review` against the rendered site at desktop, tablet, and phone widths.

- `backend/tests/perf/draft_benchmark.py --warmup 20 --iterations 200 --players 500 --events 480 --json` records hardware/runtime metadata and reports median/p95. The implementation adds this deterministic fixture and command before performance claims are evaluated.
- Board and deterministic recommendation p95 under 150 ms on the reference environment.
- Bounded simulation p95 under 400 ms on the same environment or deterministic fallback.
- One clean migration, backend test, frontend build/typecheck, and focused browser QA pass before each phase closes.

## Success Criteria

1. A first-time owner can tell from the page what the Draft Suite does, that it is read-only, which league and session are active, and what setup is still missing.
2. A standard snake draft can be prepared, run manually from start to finish, corrected after an entry mistake, reloaded, and reviewed without losing state.
3. A new mock automatically synchronizes or reuses a complete Yahoo ranking snapshot, refuses to start until the configured player/position pool can finish, and then drafts deterministic team-aware opponent picks one at a time until each owner turn without ever writing synthetic picks to a live/Yahoo room.
4. Yahoo synchronization can join an existing session idempotently without duplicating picks; shadow mode never changes missing/conflicting canonical picks without approval, evidence-gated authority is append-only/auditable, and an outage keeps manual drafting available and visibly stale.
5. Every recommendation states its numeric basis, source times, uncertainty, roster impact, and principal tradeoff.
6. The assistant automatically identifies the current team, the owner's next pick, open roster needs, positional runs, and tier cliffs.
7. Availability forecasts are immutable at the owner decision sequence; scenario branches run as cancellable persisted jobs and degrade visibly when ADP, projections, or opponent inputs are invalid.
8. Injury and role evidence is attributed and time-stamped; stale or unmatched evidence cannot silently change a recommendation.
9. Cross-league exposure is accurate and cannot alter recommendations unless the owner enables an exposure preference.
10. Post-draft replay scores any legal owner choice from the full immutable at-time surface, produces compatible waiver add/drop pairs, separates mock/live coaching evidence, and never grades decisions using information that arrived later.
11. Complete unit, API, migration, concurrency, performance, eval, and browser matrices cover ranking sync, automatic mocks, live Yahoo/manual operation, asynchronous computation, correction, degraded inputs, reload/two-tab recovery, and post-draft replay.
