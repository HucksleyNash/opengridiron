## Problem Statement

Open Gridiron can already import an NFL season schedule and calculate survivor and confidence recommendations, but the Pools UI exposes a manual game-entry form and a raw week-number input. The recurring user task is hidden behind setup and maintenance controls.

The product should instead open to the current NFL week, show the saved status of every pool entry, and let the owner make winner, loser, and confidence picks directly from the imported schedule.

## What Makes This Cool

The owner opens one page and immediately knows what still needs attention. The same imported schedule powers every pool, recommendations appear in the context of the actual matchups, and each entry moves from `Missing picks` to `Week complete` without copying schedules or tracking confidence weights elsewhere.

## Constraints

- Open Gridiron remains a private, one-owner pick companion. It does not invite participants, run a public pool, or submit picks to an external provider.
- nflverse remains the schedule source. One season import supplies every regular-season and postseason week; the application must not download a separate schedule for each week.
- Existing `Pool`, `PoolEntry`, `PoolPick`, `Game`, `DataSnapshot`, and deterministic recommendation services remain the foundation.
- Pool rules continue to control winner versus loser direction, straight-up versus against-spread basis, picks per week, maximum team reuse, confidence weights, and lock mode.
- Existing scheduled nflverse refreshes on Tuesday and Friday remain in place.
- Manual game creation remains available only as a troubleshooting fallback.
- The workspace must preserve previously imported games and saved picks when a refresh fails.

## Premises

1. The recurring workflow is week-first: open Pools, land on the inferred current NFL week, and see incomplete work.
2. The weekly schedule is the pick sheet. Recommendations decorate the schedule rather than replacing it with a separate ranked table.
3. Survivor and loser pools are entry-specific because team reuse and prior picks belong to an entry.
4. Confidence pools require one selected team per scheduled game and one unique confidence value from 1 through N, unless the pool supplies an explicit weight set.
5. Picks save locally as a draft as they change. Completion is derived from the saved card, not from a separate submit action.
6. Locks are enforced by the API, not only disabled in the browser.

## Relevant Product Conventions

Current survivor products make the entry and week explicit, show why a team is unavailable, allow changes until the applicable deadline, and track prior team usage per entry. Current confidence products use a complete weekly pick sheet with one selection per game and weights from 1 through N.

References:

- [My Survivor Pool FAQ](https://mysurvivorpool.com/support/faq)
- [PikSheet pool formats and weekly flow](https://piksheet.com/)
- [OfficePoolStop deadline behavior](https://www.officepoolstop.com/faq)

## Approaches Considered

- **Retrofit the existing Pools page:** rejected because it would ship quickly but preserve the monolithic component, fragmented requests, and awkward confidence-card writes.
- **Dedicated Pool Week workspace:** selected because it cleanly separates pool setup from the weekly ritual and gives the API one canonical view of schedule, rules, picks, recommendations, locks, and completion.
- **All-Pools Weekly Command Center:** deferred until the pool-week workflow is proven; it is a useful later aggregation layer, not a prerequisite.

## Recommended Approach

### Information architecture

- `/pools` becomes the weekly overview. It gets its bootstrap state from `GET /api/v1/pools/overview`, so the client does not need to guess a week before it can render.
- `/pools/:poolId/weeks/:week` becomes the dedicated picking workspace.
- Pool creation and rule editing move behind `Pool settings` rather than sharing the weekly workspace.
- Manual game entry moves under a secondary `Schedule troubleshooting` section.

```text
Open Pools
   |
   +--> infer current week from imported kickoff times
   |
   +--> show each pool and entry as Complete or Missing
            |
            +--> Survivor / loser: choose required team pick(s)
            |
            +--> Confidence: complete every matchup and assign unique weights
                         |
                         +--> autosave draft and recompute completion
```

The approved rough wireframe is stored at `.gstack/designs/pool-week-wireframe.png`.

### Automatic schedule availability

The existing nflverse CSV contains the full season. Automatic schedule loading therefore operates at the season level:

1. The overview and pool-week APIs read games from SQLite and return a server-derived schedule state of `ready`, `stale`, or `missing`.
2. `ready` means the season has games and its last successful nflverse snapshot is no more than 96 hours old during the active season. `stale` means games exist but the successful snapshot is older. Historical seasons with no upcoming kickoff are treated as static rather than stale. `missing` means the season has no imported games.
3. When the UI receives `missing`, it automatically calls `POST /api/v1/sync/nflverse/schedule?season={season}` once. `Loading` and the latest mutation error are client states, not persisted schedule states.
4. The sync service uses one in-process `asyncio.Lock` per season. Callers pass `trigger=missing`, `trigger=scheduled`, or `trigger=retry`. A missing-season caller records the latest snapshot ID before waiting and may coalesce only when the season becomes populated or that snapshot changes while it waits. Scheduled and Retry callers always download after acquiring the lock, so the normal Friday refresh is not skipped merely because Tuesday was less than 96 hours earlier. This is sufficient because the checked-in deployment starts one Uvicorn process.
5. The workspace invalidates its overview and pool-week queries after success and displays the imported games without a page reload.
6. If automatic import fails, the UI keeps any cached games visible, reports a sanitized message, shows the last successful snapshot time, and offers `Retry` plus troubleshooting.
7. Tuesday and Friday jobs use an NFL-season resolver: January and February map to the previous calendar year; March through December map to the current year. They refresh that season plus any matching season used by an active pool. Historical pool seasons refresh only through an explicit Retry.

The importer parses all target-season rows, preloads the existing season and linked-pick counts, validates source-key and legacy-matchup reconciliation in memory, and only then applies changes in one transaction. If a stable-key game would collide with an existing legacy matchup row, the transaction rolls back, the prior season remains intact, and the API returns `schedule_identity_conflict`. It never guesses, merges, or deletes rows during an ambiguous refresh.

The browser must not repeatedly download the schedule when a requested week is empty. An empty week can be a bye, an out-of-range selection, or a postseason boundary. Automatic import fires only when the season has zero imported games or the user explicitly chooses Retry.

The sync route must stop returning raw `str(exc)` values. It logs diagnostic detail server-side and returns a stable code such as `schedule_download_failed` with a safe message.

Before a refresh changes any stored kickoff, the importer stamps `locked_at` when the previously stored kickoff has already passed. Application startup and every scheduled refresh also stamp all due games. This prevents a later schedule correction from reopening a pick that should already have locked even when nobody visited the card at kickoff.

The parser must accept nflverse game types `REG`, `WC`, `DIV`, `CON`, and `SB`; the current generic `POST` value is not an upstream postseason type. Ingestion tests include all five accepted types.

### Current-week inference

The overview API returns a `suggested_week` for each pool season. The application has kickoff times but not authoritative game-completion status, so rollover is intentionally schedule-based:

- Choose the source week containing the chronologically next upcoming kickoff.
- If two source weeks overlap because of a postponement, the next kickoff wins; ties use the lower source week.
- After the imported season ends, choose the last imported week.
- If no schedule exists yet, use Week 1 while automatic import runs.

The UI still provides previous/next controls and a week menu. User navigation is never overridden after the page loads.

### Overview bootstrap contract

Add `GET /api/v1/pools/overview`.

Representative response:

```json
{
  "generated_at": "2026-09-09T18:00:00Z",
  "pools": [
    {
      "id": 7,
      "name": "Sunday Survivor",
      "season": 2026,
      "pool_type": "survivor",
      "suggested_week": 1,
      "inactive_entry_count": 0,
      "schedule": {
        "state": "ready",
        "source": "nflverse.schedule",
        "last_success_at": "2026-09-08T09:10:00Z"
      },
      "entries": [
        {
          "id": 21,
          "name": "Main entry",
          "active": true,
          "card_state": "draft",
          "required_count": 1,
          "selection_count": 0,
          "weight_count": null,
          "missing_count": 1
        }
      ]
    }
  ]
}
```

The overview returns only completion summaries, not full schedules or recommendation evidence. It returns active entries by default and an `inactive_entry_count`; `include_inactive=true` adds inactive entries with `active=false`, but they never contribute to missing-pick totals. For survivor/loser cards, `required_count` is `picks_per_week`, `selection_count` is the number of saved valid slots, and `missing_count` is their difference. For confidence cards, `required_count` is the number of distinct games currently assigned to the source week, `selection_count` is the number with a valid team pick, `weight_count` is the number with an allowed unique weight, and `missing_count` is the larger of the missing-selection and missing-weight counts.

`card_state` uses this precedence:

1. `needs_repair` when a legacy, moved-game, or configuration finding prevents canonical validation.
2. `locked_incomplete` when the card is incomplete and at least one missing or invalid requirement can no longer be repaired because its game or week is locked.
3. `locked_complete` when the card is complete and every required selection is locked.
4. `complete` when all required selections and weights are valid but at least one remains editable.
5. `draft` for every other valid incomplete card, including cards with some locked valid picks and remaining editable requirements.

### Canonical pool-week contract

Add:

`GET /api/v1/pools/{pool_id}/weeks/{week}?entry_id={entry_id}`

`entry_id` is required. A nonexistent entry or an entry owned by another pool returns `404 entry_not_found`. An inactive entry remains readable with `entry.active=false` and `entry.read_only=true`; writes return `409 entry_inactive`.

Representative shape:

```json
{
  "pool": {"id": 7, "season": 2026, "pool_type": "survivor", "rules": {}},
  "week": {"number": 1, "suggested_week": 1, "first_kickoff": "2026-09-10T00:20:00Z", "last_kickoff": "2026-09-15T00:15:00Z"},
  "schedule": {"state": "ready", "source": "nflverse.schedule", "last_success_at": "2026-09-08T09:10:00Z"},
  "entry": {"id": 21, "name": "Main entry", "active": true, "read_only": false},
  "card": {
    "version": 0,
    "state": "draft",
    "required_count": 1,
    "selection_count": 0,
    "weight_count": null,
    "missing_count": 1,
    "picks": [],
    "findings": []
  },
  "games": [
    {
      "id": 31,
      "source_game_key": "gsis-example-2026-001",
      "source_game_key_kind": "gsis",
      "kickoff": "2026-09-10T00:20:00Z",
      "locked": false,
      "away_team": "LAC",
      "home_team": "KC",
      "spread_home": -3.5,
      "probabilities": {
        "home_win": 0.72,
        "win_kind": "market",
        "home_cover": 0.53,
        "cover_kind": "market"
      },
      "recommendations": [
        {"team": "KC", "score": 0.69, "rationale": ["Estimated survival probability 72%"]},
        {"team": "LAC", "score": 0.28, "rationale": ["Estimated survival probability 28%"]}
      ]
    }
  ],
  "survivor_slots": [
    {
      "slot": 1,
      "current_pick": null,
      "choices": [
        {"game_id": 31, "team": "KC", "eligible": true, "reason": null},
        {"game_id": 31, "team": "LAC", "eligible": true, "reason": null}
      ]
    }
  ],
  "configuration_errors": []
}
```

`survivor_slots` is present only for survivor/loser pools, which makes eligibility slot-specific for multi-pick weeks. Confidence eligibility remains game-specific. Finding and eligibility reason enums are stable API values. Initial values are `team_used`, `selected_other_slot`, `game_locked`, `week_locked`, `blocked_team`, `not_allowed`, `foreign_game`, `foreign_team`, `duplicate_team`, `duplicate_weight`, `invalid_weight`, `moved_out_of_week`, and `legacy_pick_without_game`. A slot's current selection remains eligible for that same slot so the owner can inspect or retain it.

The endpoint composes existing models and decision services. It does not create a second schedule or recommendation store.

The current decision helpers must be refactored to return structured scoring for every team and game. The existing survivor top-ten `Recommendation` list and confidence helper's silent weight extension are presentation outputs, not sufficient domain contracts for this endpoint.

### Saving a weekly card

Add:

`PUT /api/v1/entries/{entry_id}/weeks/{week}/picks`

Request:

```json
{
  "version": 0,
  "picks": [
    {"slot": 1, "game_id": 31, "team": "KC", "confidence": null}
  ]
}
```

Add `PoolEntryWeek`, keyed uniquely by `(entry_id, week)`, with an integer `version` that starts at zero. A read returns version zero when no row exists yet. The first save creates the row idempotently, then claims the card with one conditional `UPDATE pool_entry_weeks SET version = version + 1 WHERE entry_id = :entry_id AND week = :week AND version = :expected_version`. Zero updated rows returns `409 card_conflict` unless the requested card is already identical to the canonical card, in which case the retry returns `200` with the current version.

The conditional version update is the transaction's first meaningful write. Once it succeeds, the same transaction loads current pool rules, entry state, games, locks, and picks; validates the request; replaces unlocked picks; and commits. Validation or persistence failure rolls back the version increment and every pick change. This compare-and-swap boundary works across processes and requires neither a SHA canonicalizer nor a process-local card lock.

The request always represents the complete desired unlocked portion of the card. Omitted unlocked picks are deleted. Existing locked picks are always preserved; including an identical locked pick is accepted, while attempting to change or remove one returns `409 Conflict`. Missing draft rows are represented by omission, not placeholder database rows. Survivor requests require slots in the range `1..picks_per_week`. Confidence requests are keyed by `game_id`; `slot` is omitted, assigned once as the lowest unused positive storage ordinal, and never used for identity or presentation order. Schedule corrections may change display order without changing saved-pick identity.

Incomplete drafts are valid saves. Missing survivor slots, confidence selections, or confidence weights return `200` with `card.state=draft`. Foreign games or teams, duplicate teams or weights, invalid weights, and changes to locked picks are rejected. A custom confidence weight set must contain exactly N unique positive integers for N scheduled games; otherwise the read response contains a configuration error and saves are rejected instead of synthesizing extra weights.

For survivor and loser pools, validation must enforce:

- exactly `picks_per_week` slots for a complete card;
- selected team belongs to the referenced game;
- allowed and blocked team rules;
- maximum team uses across prior weeks;
- no duplicate team inside a multi-pick week;
- the applicable game or week lock.

For confidence pools, validation must enforce:

- one pick for every scheduled game in the week;
- selected team belongs to that game;
- one unique allowed confidence weight per game;
- the default weight set is exactly `1..N` when no custom set exists;
- changing two weights is atomic so a temporary duplicate cannot be saved;
- locked game selections cannot change.

The first release enforces one entry/week/game and confidence-weight uniqueness in the shared transactional service rather than adding a database constraint that could fail on legacy rows. A later cleanup migration can add the constraint after all `needs_repair` cards are resolved.

Remove the existing `POST /entries/{entry_id}/picks` write route when the frontend migrates. Repository search found no caller beyond the old Pools page, so the new weekly-card `PUT` becomes the only pick-write contract. The existing pick-list `GET` may remain until its readers are migrated.

The client uses a latest-state autosave pump per entry/week: debounce a short edit burst, allow one request in flight, and retain only a dirty flag plus the latest local card while that request runs. After success, immediately save the latest card with the returned version when the draft changed in flight. TanStack mutation scope is a safety guard, not a queue of one mutation per edit. There are no aborted requests or client sequence numbers. A stale version or newly locked card returns `409 Conflict` with the latest canonical card and conflicting locations. The UI reloads that card, retains attempted unlocked values in memory, and offers `Reapply unlocked changes`; it does not implement a general three-way merge.

Representative successful save:

```json
{"card": {"version": 1, "state": "complete", "picks": [{"id": 88, "slot": 1, "game_id": 31, "team": "KC", "confidence": null}], "findings": []}}
```

Representative conflict:

```json
{
  "error": "card_conflict",
  "message": "The weekly card changed or a pick locked.",
  "conflicts": [{"location": ["picks", 0, "team"], "code": "game_locked", "attempted": "LAC", "canonical": "KC"}],
  "card": {"version": 2, "state": "locked_complete", "picks": [{"id": 88, "slot": 1, "game_id": 31, "team": "KC", "confidence": null}]}
}
```

Representative invalid pool configuration on a read:

```json
{
  "configuration_errors": [
    {"location": ["pool", "rules", "confidence_weights"], "code": "weight_count_mismatch", "expected": 16, "actual": 15}
  ]
}
```

Validation locations are arrays of string or integer path segments. `code` is a stable enum. `attempted` and `canonical` are nullable JSON scalars or objects. HTTP `422` is used for invalid cards, `409` for stale/locked/inactive conflicts, and `404` for missing pool or entry resources.

Representative invalid-card response:

```json
{
  "error": "invalid_card",
  "message": "The weekly card contains invalid picks.",
  "findings": [
    {"location": ["picks", 1, "confidence"], "code": "duplicate_weight", "attempted": 16, "canonical": null}
  ],
  "card": {"version": 2, "state": "draft", "picks": []}
}
```

### Server-authoritative locks

- All comparisons use UTC on the server.
- Add nullable `Game.locked_at`. Application startup, scheduled refreshes, schedule reconciliation, and any pool-week read or write stamp a game whose stored kickoff has passed. `locked_at` never clears, so a later kickoff correction cannot reopen a pick.
- For `game_start`, the referenced game locks at its stamped or current kickoff.
- For `week_start`, the whole card locks when the earliest game in the source week becomes locked.
- Before a lock is stamped, a schedule correction changes the future lock time. After it is stamped, the lock is monotonic.
- A postponed game keeps its database identity through the selected upstream source key. Prefer `gsis` when present; fall back to nflverse `game_id`, then to the legacy matchup key only when neither source ID exists. The importer stores the key kind and includes a two-refresh fixture where a game changes source week while retaining its preferred source key. If no stable source key can reconcile the row, it creates a new game and marks old linked cards `needs_repair` rather than guessing. If a reconciled game moves week, existing picks remain linked but affected cards become `needs_repair` with `moved_out_of_week`; no pick is silently moved or deleted.

### Winner and loser workspace

- The heading states the action in plain language: `Choose one winner` or `Choose one loser`.
- Entry tabs show completion and allow the owner to move between multiple entries.
- Every scheduled matchup stays visible.
- Used, blocked, or locked teams are disabled with a visible reason rather than removed.
- The top deterministic recommendation is marked in place, with probability and future-value rationale.
- Multi-pick weeks show numbered slots and the number still required.
- The sticky status bar shows `Saved automatically`, `Missing 1 pick`, `Week complete`, or `Locked`.

### Confidence workspace

- Every scheduled matchup appears once in kickoff order.
- Each row requires a selected team and a confidence weight.
- `Use suggested card` fills current deterministic selections and weights but does not prevent edits.
- Weights are changed with an accessible menu and move-up/move-down controls. Drag-and-drop is deferred until real weekly use shows it is worth the extra interaction complexity.
- Duplicate weights are rejected. Missing selections or weights remain valid drafts and keep the card incomplete.
- The header and sticky status bar show completed games out of total games.
- `Review missing` scrolls to the first incomplete or invalid row.
- Started games remain visible and locked so the weekly card retains context.

### Loading, empty, error, and stale states

- **Loading:** client-side mutation state with a skeleton schedule plus `Loading the {season} NFL schedule`.
- **Missing season:** automatically start one season import and show its progress.
- **Week has no games:** state that the imported season has no games for that week and offer week navigation, not repeated sync calls.
- **Refresh failure with cached games:** keep the server's factual `ready` or `stale` state, show the last successful refresh, and add a client `latest_refresh_failed` warning for that attempt.
- **Refresh failure with no games:** show Retry and Schedule troubleshooting; do not show the old manual-entry form as the primary workflow.
- **Probability unavailable:** allow picks from the schedule but suppress the recommendation for that basis instead of presenting a neutral fallback as evidence.
- **Legacy card needs repair:** preserve the rows, identify the exact anomaly, and let the owner attach or replace unlocked legacy picks. Nothing is deleted during migration.

### Legacy compatibility

- Existing `PoolPick` rows with `game_id=null`, duplicate game references, invalid teams, or invalid confidence weights remain readable.
- The overview marks affected entry/weeks `needs_repair`; the workspace lists each issue and permits repair only while the applicable slot is unlocked.
- A migration never guesses a game from team text and never deletes a legacy pick.
- The application-level validator prevents new invalid cards immediately. The database uniqueness constraint is a separate follow-up after repair debt reaches zero.

## Security and Trust Boundaries

- Schedule downloads remain server-side and use the existing fixed nflverse URL.
- The browser receives source names and timestamps but never local cache paths.
- API validation treats browser eligibility and lock displays as hints, not authority.
- A saved pick must reference a game in the pool's season and requested week.
- Automatic schedule failure messages use stable error codes and must not expose filesystem paths, raw upstream response bodies, or exception strings.
- Card versions provide conflict detection, not authorization; the owner-session boundary remains unchanged.

## NOT in scope

- An all-pools combined editing screen. The overview links to one dedicated pool-week workspace at a time.
- Drag-and-drop confidence ranking. The first release uses accessible menus and move controls.
- A general three-way merge editor. The first release reloads canonical state and offers one reapply action for still-unlocked attempted changes.
- Background-worker progress for schedule imports. The current single-process synchronous import uses client pending/error state.
- A database uniqueness constraint on `(entry_id, week, game_id)` until legacy cards have been repaired. This follow-up is recorded in `TODOS.md` with its readiness condition.
- Multi-process schedule-import coordination. The checked-in deployment starts one Uvicorn process; the card write path itself remains process-safe through SQLite.
- A speculative generic deadline-rule engine. Implementation blocks on the three real pool rule matrices and extends the schema only for demonstrated rules.

## Success Criteria

1. Creating or opening a pool with no local season schedule automatically imports the season and renders the requested week without manual game entry.
2. `GET /pools/overview` boots the page without a client-supplied week, returns a deterministic suggested week for each pool, and never resets a week the user explicitly navigated to during that visit.
3. The overview accurately identifies every draft, complete, locked-incomplete, locked-complete, and needs-repair entry/week.
4. A survivor or loser selection saves, reloads, respects prior team use, and cannot be changed after its configured lock.
5. A confidence card cannot become complete until every scheduled game has one pick and every allowed weight is used exactly once.
6. Reordering confidence weights saves atomically without transient duplicate-weight failures.
7. A failed schedule refresh never deletes cached games or saved picks.
8. Schedule and probability freshness and provenance are visible on the weekly workspace; unavailable probabilities do not produce recommendations.
9. Manual game entry is absent from the normal weekly workflow but remains reachable through troubleshooting.
10. Two tabs cannot overwrite the same entry/week card, different weeks do not conflict, concurrent imports for the same season coalesce, and rapid edits retain only the latest pending draft.
11. Legacy invalid picks remain visible as needs-repair items and are never silently deleted.
12. Backend tests, migrations, formatting, frontend type checking/build, and focused browser QA pass.

### Versioned weekly-card save

```text
PUT desired unlocked card + expected version
              |
              v
ensure PoolEntryWeek row exists (version 0)
              |
              v
UPDATE version = version + 1 WHERE version = expected
       | zero rows                         | one row
       v                                   v
canonical card identical?          writer lock now held
  | yes          | no                       |
  v              v                          v
200 retry      409 latest card      load latest rules/games/picks
                                             |
                                             v
                                  evaluate and validate full card
                                     | invalid       | valid
                                     v               v
                                  rollback       replace unlocked picks
                                  409/422             |
                                                      v
                                            evaluate result and commit
```

### Latest-state autosave

```text
local edit
   |
   +--> update visible draft immediately
   +--> mark dirty and debounce
              |
              v
       request already in flight?
          | yes             | no
          v                 v
 keep only latest draft   send full card once
          |                 |
          +--------+--------+
                   v
             response arrives
          | success          | failure/conflict
          v                  v
 use returned version     keep attempted draft
 dirty again?             show retry/reapply
   | yes  -> send latest
   | no   -> Saved automatically
```

### Season reconciliation

```text
download full nflverse CSV
          |
          v
parse requested season + normalize source keys/probability provenance
          |
          v
prefetch existing games and linked-pick counts for that season
          |
          v
match preferred source key -> fallback source key -> legacy matchup
          |
          +--> ambiguous/collision: rollback all, keep last good season,
          |                        return schedule_identity_conflict
          |
          +--> safe matches: stage creates/updates/moves and due locks
                                   |
                                   v
                         commit games + successful snapshot
```

## Production Failure Modes

| Codepath | Realistic failure | Test | Handling | User-visible result |
|---|---|---|---|---|
| Missing-season import | GitHub timeout or 502 | Yes | Preserve database/cache; typed `schedule_download_failed` | Retry and troubleshooting with last success time |
| Schedule reconciliation | Stable key collides with legacy matchup | Yes | Roll back full refresh | `schedule_identity_conflict`; prior schedule remains |
| Schedule parsing | Odds or provenance unavailable | Yes | Store `unavailable`; suppress recommendation | Matchup remains pickable without misleading evidence |
| Suggested week | No games or overlapping weeks | Yes | Deterministic Week 1/next kickoff/last week rules | Stable week navigation |
| Overview composition | One pool has malformed legacy picks | Yes | Canonical evaluator returns `needs_repair` | Exact repair findings, not a failed whole page |
| Pool-week read | Entry belongs to another pool or is inactive | Yes | `404 entry_not_found` or read-only response | Clear unavailable/read-only state |
| Card validation | Duplicate team/weight or invalid configuration | Yes | Roll back version and picks; `422` | Exact locations and codes remain editable |
| Card concurrency | Two tabs submit version N | Yes | Exactly one conditional update wins | Losing tab gets canonical card and Reapply action |
| Lock passage | Kickoff passes while card is open | Yes | Transaction reads/stamps latest lock and rolls back edit | Pick remains canonical and displays Locked |
| Autosave | Network fails while newer edits exist | Yes | Keep dirty latest draft in memory | Visible retry; no false Saved state |
| Migration | Existing database contains malformed legacy rows | Yes | Nullable additions and no destructive backfill | Deployment succeeds with `needs_repair` preserved |
| Rules | Real pool rule is not representable | Rule-matrix gate | Stop implementation and extend schema deliberately | No silently incorrect picks or deadlines |
